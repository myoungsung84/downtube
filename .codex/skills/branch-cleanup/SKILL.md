# Branch Cleanup

Downtube 저장소에서 작업 종료 후 브랜치를 정리할 때 사용하는 절차다.

## 사용 시점

- 사용자가 `브랜치 정리해`, `현재 작업 브랜치 삭제해`, `merge 끝났으니 브랜치 cleanup 해`처럼 브랜치 정리를 직접 요청했을 때 사용한다.
- 사용자가 `브랜치 삭제해`, `로컬/원격 브랜치 정리해`, `작업 끝났으니 브랜치 치워`, `merge 끝난 브랜치 삭제해`처럼 비슷한 의미로 요청했을 때도 같은 skill을 적용한다.
- 로컬 브랜치 삭제와 필요 시 원격 브랜치 삭제, 정리 후 `main` 최신화까지 한 흐름으로 처리해야 할 때 사용한다.
- 현재 브랜치가 `main`인지 여부에 따라 삭제 미수행 또는 정리 수행을 분기해야 할 때 사용한다.

## 핵심 원칙

- 기준 브랜치는 항상 `main`이다.
- 현재 브랜치가 `main`이면 삭제 작업은 수행하지 않는다.
- 현재 브랜치가 `main`인 경우에도 기준 브랜치 최신화를 위해 `main`에서 `git pull`은 수행한다.
- 체크아웃 중인 브랜치는 바로 삭제할 수 없으므로, 삭제 전에 반드시 `main`으로 이동한다.
- 브랜치 정리 중에는 `main` 이외의 다른 임의 브랜치로 이동하지 않는다.
- 로컬 브랜치 삭제는 기본적으로 `git branch -d`를 우선 검토하고, `git branch -D`는 예외적으로만 사용한다.
- 원격 브랜치는 `origin`에 실제로 존재할 때만 삭제한다.
- 원격 존재 여부 확인 없이 `git push origin --delete <branch>`를 바로 실행하지 않는다.

## 작업 절차

1. 현재 체크아웃된 브랜치명을 먼저 확인하고 기록한다.
2. 현재 브랜치가 `main`인지 먼저 판단한다.
3. 현재 브랜치가 `main`이면 삭제 작업은 수행하지 않는다.
4. 현재 브랜치가 `main`인 경우에도 기준 브랜치 최신화를 위해 `main`에서 `git pull`을 수행한다.
5. 현재 브랜치가 `main`이 아니면 정리 대상으로 본다.
6. 정리 대상 브랜치가 확인되면 먼저 `main`으로 이동한다.
7. `main`으로 이동한 뒤 방금 전 브랜치를 로컬에서 삭제한다.
8. 로컬 삭제는 아래 기준으로 선택한다.

- 기본은 `git branch -d <branch>`를 사용한다.
- 이미 병합된 브랜치 정리이거나 안전하게 삭제 가능한 경우에는 `git branch -d <branch>`를 유지한다.
- 병합되지 않았지만 사용자가 강제 정리를 명시적으로 요청했고 삭제 의도가 분명한 경우에만 `git branch -D <branch>`를 사용한다.

9. 원격 브랜치 존재 여부는 명시적으로 확인한다.

- 기본 확인 예시는 `git ls-remote --exit-code --heads origin <branch>`다.
- 이에 준하는 방식으로 원격 브랜치 존재 여부를 분명하게 확인한 뒤에만 삭제를 진행한다.

10. 원격 브랜치가 있을 때만 `git push origin --delete <branch>`로 삭제한다.
11. 원격 브랜치가 없으면 로컬 브랜치만 삭제하고 원격 삭제는 건너뛴다.
12. 브랜치 정리가 끝나면 `main`에서 `git pull`까지 수행한다.

## 실행 순서 예시

1. 현재 브랜치 확인 및 기록
2. 현재 브랜치가 `main`인지 판단
3. `main`이면 삭제 없이 `git pull`
4. `main`이 아니면 `main`으로 이동
5. 이전 브랜치 로컬 삭제
6. `origin`에 있을 때만 원격 브랜치 삭제 후 `main`에서 `git pull`

## 실수 방지 체크리스트

- 현재 브랜치가 정말 `main`이 아닌지 먼저 확인한다.
- 삭제 대상 브랜치명을 기록한 뒤 진행한다.
- 현재 브랜치가 `main`이면 삭제를 수행하지 않고 `git pull`만 한다.
- `main` 이동 전에는 삭제 명령을 실행하지 않는다.
- 로컬 삭제는 기본적으로 `-d`로 충분한지 먼저 검토한다.
- 강제 삭제는 사용자가 의도를 분명히 밝혔고 `-d`로 처리할 수 없을 때만 `-D`를 사용한다.
- 원격 삭제 전에는 `origin`에 같은 브랜치가 실제로 존재하는지 명시적으로 확인한다.
- 정리 후 현재 브랜치가 `main`인지 다시 확인한다.
- 정리 마지막 단계에서 `main`의 `pull`까지 빠뜨리지 않는다.

## 복구 및 주의사항

- 브랜치를 잘못 삭제했더라도 대체로 `git reflog` 또는 마지막 커밋 해시로 복구할 수 있다.
- 원격 브랜치까지 삭제했더라도 커밋 해시가 남아 있으면 해당 커밋으로 브랜치를 다시 만들고 push할 수 있다.
- 다만 reflog 정리나 가비지 컬렉션 이후에는 복구가 어려울 수 있으므로, 삭제 전에는 대상 브랜치와 복구 기준 커밋을 신중히 확인한다.

## 삭제 후 확인 항목

- `git branch --show-current` 결과가 `main`인지 확인한다.
- 삭제 대상 로컬 브랜치가 `git branch --list` 결과에서 사라졌는지 확인한다.
- 원격 브랜치를 삭제한 경우 `git ls-remote --heads origin <branch>` 또는 이에 준하는 확인 결과에서 사라졌는지 확인한다.
- 현재 브랜치가 처음부터 `main`이었던 경우에는 삭제가 미수행되었음을 최종 보고에 분명히 적는다.
- `main`이 `git pull` 이후 최신 상태인지 확인한다.

## 출력 규칙

- 최종 보고는 아래 형식을 그대로 사용한다.
- 삭제를 수행하지 않은 경우에도 이유를 분명하게 적는다.
- 원격 브랜치가 없어서 로컬만 정리한 경우 그 사실을 적는다.
- 현재 브랜치가 `main`이라 삭제를 수행하지 않은 경우에는 `삭제 미수행 사유: 현재 브랜치가 main`을 명시한다.

## 사용 예시

```text
브랜치 정리해
현재 작업 브랜치 삭제해
merge 끝났으니 브랜치 cleanup 해
```

```text
[done]

1. 정리 대상
- 현재 브랜치:
- 삭제 대상 브랜치:

2. 수행 내용
- `main` 이동 여부
- 로컬 브랜치 삭제 결과
- 원격 브랜치 삭제 여부
- `main` pull 여부

3. 확인 포인트
- 현재 기준 브랜치
- 원격 브랜치 존재 여부 확인 결과
- 삭제 미수행 사유 또는 삭제 수행 결과
- 복구 시 참고할 마지막 커밋 또는 확인 방법
```
